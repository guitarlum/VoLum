# F6 — Bring Your Own Amp (+ Custom-area foundation)

Plan a custom-amp builder plus the shared "Base / Custom" area that hosts all user-supplied content. The Custom area must be unobtrusive and secondary to the curated gallery (this is a ~10% feature; the default view must not be crowded). This ticket owns the FOUNDATION that F7 (BYO IR) and F8 (Import Pedals) build on: how the Custom area is entered, and where user content (`.nam` / `.wav` files + profile metadata) is stored on disk (user profile dir, NOT `rigs/`; see `VoLumPaths.h`). A custom amp is a named profile with up to 4 speaker slots: DIRECT (AMP, no cab, optional) plus up to 3 free-named cab/speaker types, entered via a text box with autocomplete from names already used in the profile, capped at 3 so the speaker-row layout (`VoLumSpeakerRow.h`) never has to change. Channels are integers representing gain stages (document VoLum's `Speaker-AmpCode-Channel.nam` convention in the docs and in the builder UI, with the 2203/2204 multi-capture rationale: separate captures preserve each amp's natural gain range). In the builder/editor the user uploads each `.nam` and assigns it to a (speaker type, channel); the builder pre-fills a best-effort draft by parsing the filename when it matches VoLum's convention, but manual assignment is the reliable primary path and always overrides. Sparse / partial uploads are first-class: the (speaker x channel) availability is a sparse matrix, so switching speaker must auto-snap to a valid channel for that speaker (and switching channel must adapt the available speakers), and empty speaker slots are disabled — reuse the per-speaker discovery already in `volum::DiscoverChannels` (`VoLumPaths.h`). Custom amps appear in the sidebar under the Custom area and are selectable like bundled amps, and presets (F5) can reference them. Decide: whether custom amps extend `VoLumAmpeteCatalog.h` or live in a parallel custom-catalog model that composes with the static arrays; per-amp settings persistence for custom amps; keyboard navigation into custom amps; create/edit/delete/rename flow and validation (duplicate names, missing files, moved files). Produce a feature ticket with: Custom-area UX spec, user-content storage schema + location, custom-amp profile schema, builder/editor UI spec, sparse-grid navigation/snap rules expressed as pure helpers (testable like `VoLumProcessingPlan.h`), tests (profile round-trip, sparse-grid snap logic, discovery, load smoke), docs EN/DE documenting the naming convention + screenshots, changelog. Do not implement.

Work must happen on a dedicated feature branch off the latest `dev`, named `feature/bring-your-own-amp`. Do not commit to `dev` or `main` directly. The branch is merged back into `dev` only after the ticket's acceptance criteria are met and tests/docs/changelog are in place. Never promote to `main` outside of a release.
