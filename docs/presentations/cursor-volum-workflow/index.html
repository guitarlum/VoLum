02  /  taking it over

The brownfield takeover playbook

  • Wrote AGENTS.md as a map, not a manual Scope (ours vs. vendored), "Start Here" routing, UI file map, fast commands.
  • Boundary discipline — know what not to touch Agents never edit iPlug2 / NeuralAmpModelerCore / eigen. Half of brownfield safety is a fence.
  • Built a feedback loop: a handful → 41 test files Apr 7 doctest suite → Apr 12 "VoLum unit tests" → steady growth. The agent self-verifies.
  • Characterization / golden tests pin behavior before refactor test_golden_dsp / _presets / _rigs, test_nam_rigs, pre-pedal captures.
  • Proactive decomposition, with commit evidence ~500-line split rule: Apr 23 split VoLumControls.h, Jun 29 decompose NeuralAmpModeler.cpp.
  • Stay mergeable with upstream upstream-sync skill + a visible "// VoLum:" fence in upstream-equivalent files.
  • Rollback hygiene Single coherent commits + a changelog line — any legacy break is one git revert away.

Takeaway: give the agent a map, a fence, and a feedback loop before you ask it to change anything.

03  /  the thesis

Scoped & lazy-loaded — not minimal.

We don't have few rules. We have a tiny router and rules/skills that load only when a task touches them. Context stays small, so tokens stay cheap and the model stays focused.

05  /  rules

Rules = guardrails, mostly silent

  • Always-on: the workflow safety-net, plan lifecycle, git-remote quirk
  • Scoped: UI, state/params, native DSP, packaging, submodules — fire only on matching work
  • They encode hard-won constraints: PowerShell 5 (no &&), here-strings for commits, refactor at ~500 lines
.cursor/rules/vo-lum-workflow.mdc 
## Tests are mandatory, not optional
- Write tests for every confirmed feature/bugfix.
  Do not wait for the user to ask.
- New DSP behavior → doctest: no NaN,
  passthrough at zero mix, bounded output, all modes.
- If a bug was caused by a missing test,
  add the test that would have caught it.

## Execution
- You run builds/tests here — don't just tell.
- After failures: diagnose, fix, retry.
06  /  skills

Skills = heavy playbooks, pulled in only when invoked

release-manager

PR + GitHub release flow, merge-conflict resolution, artifact checks across main/dev.

native-build-debugger

Diagnose Win/mac build, packaging, installer, VST3, and CI failures.

upstream-sync

Bump NAMCore, cherry-pick upstream, keep the fork mergeable.

deep-reverse-engineering

Local-only research to find a copyable DSP algorithm (pitch, octaver, tremolo). Global.

captain-hindsight · occams-razor

Opt-in retro that ends in tracked artifacts, and the periodic audit that prunes them. Global — every repo gets them.

caveman

Ultra-compressed replies — ~75% fewer tokens, full technical substance kept.

A rule says "watch out"; a skill says "here's the whole procedure" — and it costs nothing until you need it. Anything repo-agnostic moves out to the global scope, so it isn't re-invented per project.

08  /  choosing the artifact

Rank by delivery reliability, not by ease of writing

The same lesson can live in five places. They are not equivalent — only some of them are guaranteed to arrive at the moment they matter.

  • Script — anything mechanically checkable. Costs zero context until it runs and cannot be forgotten.
  • Glob-scoped rule — knowledge bound to specific files. Attaches itself when those files are opened.
  • Skill — a task with no file signature: release flow, upstream sync, build debugging.
  • Always-applied rule — only what must be known before any file is touched. Every line is paid in every session.
  • AGENTS.md — routing index and commands. No detailed guidance.
.cursor/rules/ai-artifact-authoring.mdc 
## Anti-patterns
- A skill that wraps a glob rule.
  The rule already fires on those files, earlier
  and without depending on the model choosing
  the skill. Put the knowledge in the rule.
- Prose restating what a script enforces.
  Name the script instead.
- Detail in an always-applied rule that only
  matters for one file set.

## Pointer discipline
Point only at sources guaranteed to be loaded:
always-applied rules and AGENTS.md.
# Never replace a fact in one glob rule with a
# pointer to another - it may not be attached.

So we deleted two skills: volum-ui-change and volum-param-state-change each wrapped a glob rule that already fires on the same files. Deleting guidance can be an upgrade.

09  /  guidance rots

Wrong guidance is worse than verbose guidance

Overhead only costs tokens. A stale pointer actively sends the next agent to a path that isn't there. So instead of writing "keep the docs in sync," we made it fail the build — three checks wired into run-tests-win.ps1, so they run unasked.

check-agent-artifact-links

Every backticked path in a rule, skill, or AGENTS.md must resolve — and every globs: pattern must match at least one file, because a glob that matches nothing never fires and is pure cost.

check-test-source-parity

41 doctest files, two build descriptors, one source of truth — so no test is silently left out of the run it was written for.

check-shell-exec-bits

Git on Windows drops the exec bit and only the macOS runner notices. Caught in seconds instead of an hour into CI.

The receipt: the link check failed its own author. The brand-new rule pointed a glob at a gitignored directory, so it matched nothing on a clean checkout — the model that wrote it and the audit pass that reviewed it both missed it, and the script caught it on the first CI run.

10  /  the key mental model

Binary vs. subjective quality

"A compressor every model can build" is not "a compressor that sounds great." That distinction decides how much model you spend.

Binary — pass / fail

Builds compile. Tests are green. Installer runs. Chunk round-trips. Output is finite & bounded.

→ A cheaper/faster model is fine. The scripts tell you if it's right.

Subjective — does it feel good?

Tone, sag, the "give" of a compressor, an octaver that tracks, a tremolo that breathes. No green checkmark exists.

→ Frontier models + listening loops + reference-plugin reverse-engineering.

11  /  model selection

Match the model tier to the task shape

  • Docs, config, wording, mechanical edits → fast tier
  • Architecture, tricky refactors, DSP tone, anything safety-critical → strong reasoning / frontier
  • /grill-me before drafting a non-trivial plan — measure twice
  • Every plan ends with an Implementation Recommendation (model + skills + why)
.cursor/rules/measure-twice-cut-once.mdc 
# Measure Twice, Cut Once

## Measure Twice
For non-trivial/ambiguous work, prefer /grill-me.

## Cut Once — handoff
End every plan with Implementation Recommendation:
  Model:  pick by task shape, not habit
  Skills: attach before coding / opt-in retro
  Why:    one line tied to the task

# Never hardcode one model as a universal default.
12  /  what worked

What worked — by value axis

Output quality

Tests are mandatory + golden/characterization tests. /grill-me planning. Scripts give deterministic verdicts, not vibes.

Quality of life

Router keeps context tiny. Agent runs builds itself. Auto screenshots + changelog lines. One coherent commit = easy revert.

Token savings

Lazy-loaded scoped rules. Small AGENTS.md. caveman mode when volume beats prose. Skills cost nothing until invoked.

The same architecture that keeps output correct also keeps it cheap and pleasant to drive.

13  /  the scars

What we changed — candidly

Rules aren't written once. They accumulate, rot, and need pruning. The honest arc:

  • Rules accumulated faster than they earned their keep
  • PowerShell && / heredoc pain bit us repeatedly before we codified it
  • The same skill lived in the repo and globally — one silently shadowed the other, and the two drifted for weeks
  • Now we prune on purpose, keep one copy of every skill, and turn anything checkable into a script

14  /  next

Where we'd sharpen it next

01 · shrink the "subjective" zone

Extend the existing golden tests toward perceptual/tone regression (RMS + spectral diff) on top of the REAPER harness, so more tone quality becomes measurable.

02 · a DSP listening checklist skill

Make subjective evaluation repeatable: a structured pass (transients, noise floor, zipper, tail, extreme settings) instead of ad-hoc listening.

03 · scheduled occams-razor pass

Run the audit on a cadence (via the loop skill) so rule bloat is caught early, not during a big cleanup.

04 · guidance checks in the fast lane

The link check currently rides along with the Windows test job, so a dead pointer costs four minutes to discover. Move it into the 40-second formatting job — and add the one check we still lack: that the AGENTS.md file map matches the actual header split.

16  /  steal this

Replicate it on your repo

  • Write a tiny router + file map first (AGENTS.md)
  • Draw a fence around vendored code the agent must not touch
  • Pin behavior with characterization / golden tests before you refactor
  • Add a rule only when a mistake recurs — not preemptively
  • Match model tier to binary-vs-subjective quality
  • Promote reusable playbooks into skills (they're free until used) — and keep exactly one copy of each
  • Make verification a script the agent runs, not advice it gives
  • Pick the artifact by delivery reliability: script > glob rule > skill > always-on rule
  • Prune on a schedule — and let a check fail the build when guidance goes stale

A big brownfield gets tractable when the agent has a map, a fence, a feedback loop, and just enough rules.
