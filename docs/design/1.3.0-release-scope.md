# VoLum 1.3.0 — release scope (working draft)

Status: **draft, scope NOT locked.** This is a decision-support document for the
scoping conversation, not a commitment. Nothing here is scheduled until the open
questions in §7 are answered.

Baseline as of 07/29/2026: latest published release is **v1.2.0**; **1.2.1 is
still in flight** on `release/1.2.1` (version files bumped, changelog written, tag
not yet cut). 1.3.0 branches off `dev` *after* 1.2.1 lands on `main` and `main` is
merged back into `dev`.

---

left alone:

- **Close issues [#21](https://github.com/guitarlum/VoLum/issues/21) and

  larger than it is and leaves two reporters thinking they were ignored. Closing

  of user who bothered to file.
- **Triage [#22](https://github.com/guitarlum/VoLum/issues/22).** Filed with the

- **Archive F4.** `backlog/README.md` claimed A2-Lite was pending merge to `dev`;

Also note issue #21 carries a second, unrelated request in its postscript: *"since
there are only a few cabs included, it would be worthwhile to focus on getting

has no backlog item. It may be worth more to users than any feature listed below.

## 2. Sizing scale

Rough, and deliberately coarse. **S** = one day or less. **M** = two to four days.
**L** = one to two weeks. **XL** = more than two weeks or genuinely unknown.
Estimates assume focused days, not calendar days.

## 3. Feature candidates

- **F14 — update notifier.** M (2-3 days). Design settled, see
  `backlog/F14-update-notifier.md`. Subtle in-app "new version available" notice
  in standalone and plugin, fed by a static `appcast.json`. Notify-only;
  auto-update is out of scope and blocked on code signing. **Timing argument:** it
  produces no value for anyone until the release *after* the one that ships it,
  so every release it slips costs a full cycle of reach. Cheapest way to stop
  depending on Reddit and YouTube for release discovery.
- **F9 — MIDI (Bank Select + Program Change first).** L. The F9 1.2.1 spike was
  gated out for good reasons: iPlug calls `ProcessMidiMsg()` on the audio thread
  while amp/channel/preset selection touches the content registry, the filesystem,
  async model queues and UI controls. Doing it safely needs a lock-free command
  handoff and **one headless selection service shared by mouse, keyboard and
  MIDI** — that second part is a real refactor, not a feature bolt-on. The F9 doc
  explicitly says "revisit for 1.3.0". This is the single biggest item on the list
  and would define the release if included. Arbitrary CC mapping and MIDI-learn
  should stay a later layer.
- **F11 — Octaver deep research.** L. Measured-reference rework of the Octaver
  mode using the local `deep-reverse-engineering` skill.
- **F12 — Tremolo deep research.** M-L. Validate the three POST Tremolo voices
  against measured references; fix any that is not an honest emulation.
- **F13 — custom-amp artwork reroll.** M. Expanded procedural styles plus a
  deterministic reroll, with a style-id/seed schema migration. Self-contained,
  visible, low risk — a good filler item.
- **F10 — settings import/export.** M. Never scoped in detail.
- **O1 / [#17](https://github.com/guitarlum/VoLum/issues/17) — Linux.** XL, spike
  first. Can run in parallel with everything else because it touches packaging
  more than product code.
- **[#20](https://github.com/guitarlum/VoLum/issues/20) — CLAP format.** Unknown,
  needs a spike before it can be sized. No backlog item exists yet. The blocking
  unknown is what CLAP support looks like from the current vendored iPlug2 — this
  should not be committed to 1.3.0 without that answer.
- **Better bundled cabs / IRs.** Unknown. Content, not code. No backlog item; see
  §1.

## 4. Quality and infrastructure candidates

- **Code signing (Windows + macOS).** Not currently a backlog item, and arguably
  the highest-leverage non-feature on this list. Every user today clicks past
  SmartScreen on Windows and a Gatekeeper warning on macOS, which costs installs
  from exactly the non-technical audience F14 is trying to reach. It also
  **unblocks any future auto-update**. The work itself is small-to-medium, but it
  has real-world lead time and cost: an Apple Developer account, and a Windows OV
  or EV certificate that may ship as a physical hardware token. If it is wanted
  for 1.3.0, procurement has to start well before the code does.
- **P2 — RT/perf hardening.** L, gated on macOS TSan CI. Lock-free staging drain,
  buffer capacity assert, async IR load, throttled settings save.
- **Q2 — decompose `VoLumCustomUi.h`.** M. Pure hygiene, phased low-to-high risk.
- **Q4 — screenshot harness + custom-amp seeding.** M. Pays for itself over time
  in docs/screenshot work.
- **[#16](https://github.com/guitarlum/VoLum/issues/16) — tier CI runtime.** S-M.
  Faster feedback on every subsequent item.
- **Q1 — regression pins.** S. Best folded into whatever perf/refactor pass runs,
  rather than scheduled standalone.
- **Q3 — custom-content correctness.** S. Confirmed niche/latent, no urgent
  user-facing bug remains.
- **R2, R3, R4 — repo hygiene and upstream sync.** S each.
- **D1 — docs polish.** S, folded in continuously.

## 5. Wildcards needing a decision

- **Android.** `feature/android-poc` and `feature/android-ui-proposals` exist
  (last touched 07/04 and 07/10) but are not represented in the backlog at all. Is
  this a 1.3.0 deliverable, a separate product track, or an abandoned spike? It
  cannot be scoped here without that answer.
- **`feature/ai-artifact-audit`** (07/27) — unclear whether this is release scope,
  tooling, or exploration.

## 6. Three possible shapes

Offered to make the trade-off concrete, not because one is obviously right.

**A. Reach and trust.** F14 update notifier, code signing, close out the stale
issues, better cabs, D1 docs, plus one visible feature such as F13. Roughly 1-2
weeks of build time plus signing lead time. Nothing here is glamorous, but it
compounds: every later release reaches more people and installs more cleanly. Best
fit for the problem that started this conversation.

**B. Features.** F9 MIDI as the headline, plus F14 (cheap, and wants to be early)
and one of F11/F12. Roughly 3-4 weeks. MIDI would dominate the release and drag
the selection-service refactor in with it, which is genuinely valuable but is
where the schedule risk lives.

**C. Sound quality.** F11 and F12 deep-research passes plus better bundled cabs,
with F14 alongside. Roughly 2-3 weeks. Speaks directly to the tone-chaser audience
and to the second half of issue #21, but produces no headline feature bullet.

F14 appears in all three deliberately: it is small, it is the only item that gets
*worse* the longer it waits, and it makes every subsequent release more effective.

## 7. Open questions to lock scope

1. **Which shape** — A, B, C, or a mix? What is the headline for the release notes?
2. **Is MIDI in?** It is the largest single item and the main schedule risk. If it
   is in, most other features should come out.
3. **Appetite for code signing?** It has cost and procurement lead time, so it
   needs deciding before the code work starts, not during.
4. **Android — in, separate track, or dead?**
5. **Target date**, or is 1.3.0 done-when-done?
6. **Does CLAP get a sizing spike** before scope locks, or is it deferred outright?

## 8. Definition of done

Standard flow per `.cursor/rules/volum-workflow.mdc` and the `release-manager`
skill: every item merged to `dev` with tests, changelog line, and EN/DE docs in
sync; CI green on `dev`; release PR promotes `dev` to `main`; Release Native
workflow cuts the tag and uploads the six draft assets; notes reviewed and
published by hand; `main` merged back into `dev`.

If F14 ships in this release, one extra one-time step applies: **enable GitHub
Pages on the `gh-pages` branch**, otherwise the manifest 404s and the notifier
silently does nothing.
